# Learn How to Use Google Docs for UX Documentation

## Research & Learn

**What types of UX documentation are typically created in Google Docs?**
Google Docs is usually for the writing side of UX work, not the visual side, that's what Figma is for. Things like research summaries, interview notes, personas, journey maps written out as text, design rationale, usability test reports, and meeting notes all tend to live in Docs since they're easy to share and comment on.

**How should design decisions and rationale be documented for future reference?**
The most useful way is to write down what was decided, why it was decided, and what other options were considered but ruled out. Just saying "we went with X" isn't much help six months later when someone asks why. Including the reasoning, like a user need or a constraint that drove the choice, means someone can actually follow the logic later instead of just seeing the end result. Dating things and linking back to the research that backed it up helps too.

**What is the best way to structure user research findings to make them easy to read?**
Start with a short summary and the key takeaways up top, before anyone has to dig into the details. Then break the findings into clear sections, by theme or user group, instead of one big wall of text. Headings and bullet points make it skimmable, since most people reading a research doc just want the main points, not the whole story. Adding a few real quotes from participants also helps it feel like actual people, not just abstract findings.

**How can UX documentation be used to support accessibility and inclusive design?**
Documentation is where accessibility stuff actually gets captured and passed along, otherwise it tends to get lost between design and development. Writing down things like color contrast choices, keyboard navigation, screen reader behavior, and different user needs directly in the design notes means developers aren't left guessing what "accessible" actually means for that feature. It also gives the team something to check back against later instead of relying on memory.

## Reflection

**If you conducted a user testing session, how would you document the results?**
I'd start simple, who was tested, what task they were given, and the date. Then I'd write down what actually happened, where they got stuck, where it went smoothly, and any quotes that stood out. I'd keep what actually happened separate from what I think it means, so it's clear which is which. Then a short summary at the end with the main takeaways, so someone skimming the top still gets the point.

**How can a well-structured UX document help prevent miscommunication between teams?**
It gives everyone the same source of truth instead of relying on someone remembering a meeting or a decision explained once out loud. If a developer or PM wonders why something looks a certain way, they can just check the doc instead of chasing someone down, which cuts down on things getting explained differently every time.

**What challenges might arise when writing UX documentation, and how can you avoid them?**
Probably the biggest one is writing too much, dumping in every detail with no real structure, so nobody actually reads it. Keeping a clear summary up top and only including what's genuinely useful later helps with that. The other issue is docs going stale, decisions get written down, but the product keeps changing and the doc never gets updated. Making updating the doc part of the process, not a one-off task, keeps it actually useful.
